# Development Guidelines

This document defines the workflow, conventions, and engineering standards for developing `aydb`.

## 1. Language Policy

* **Repository Artifacts (English Only):** All files committed to the repository—including documentation under `docs/`, `README.md`, source code comments, docstrings, error messages, test descriptions, and Git commit messages—must be written in **English**.
* **Interactive Discussions:** Interactive design discussions and pair-programming conversations outside the repository may be conducted in the developer's preferred language.

## 2. Git & Version Control Policy

* **Never Push Automatically:** Do **not** execute `git push` (or any remote-mutating Git command) automatically. Pushing to a remote repository must only be performed by the user or when explicitly instructed by the user for a specific commit/branch.
* **Clean, Atomic Commits:** Keep commits focused on a single logical change (e.g., design documentation update, a specific sub-module implementation, or a self-contained test suite).
* **Pre-Commit Checks:** `.githooks/pre-commit` rejects a commit that fails `cargo fmt --check` or `cargo clippy --all-targets -- -D warnings`, and when files under `formal/lean/` are staged and `lake` is installed locally, runs `lake build`, `check_axioms.py`, and `lake exe aydb-trace-check fixtures/*.ndjson` (skipping with a notice if `lake` is absent locally). Enable it once per clone with `git config core.hooksPath .githooks`. CI enforces all Rust checks plus the dedicated `formal` Lean 4 job unconditionally.

## 3. Design-First, Phase-by-Phase Workflow

`aydb` is developed incrementally through the phases and future search milestones outlined in [ARCHITECTURE.md](./ARCHITECTURE.md). To maintain architectural integrity and ensure every subsystem is thoroughly understood before code is written:

1. **No Premature Implementation:** Do not jump ahead into writing production code for a phase or subsystem before its detailed design has been discussed and agreed upon.
2. **Subsystem Detailed Design First:** Each phase is broken down into concrete subsystems (e.g., in Phase 1: PAL/VFS, `boot_meta.db`, fixed-size WAL, MemTable & immutable `idx`/`blob` segments, crash recovery, and LRU eviction). Before implementing a subsystem, we first clarify and document:
   * Exact binary layouts, alignment invariants, and endianness.
   * Concurrency model, lock granularity, and lifetime/handle ownership.
   * Failure modes (torn writes, partial flushes, `SHARING_VIOLATION`, SMB write-behind errors) and how they are tested.
   * Public and internal Rust API boundaries.
3. **Incremental Verification:** Each subsystem must be accompanied by deterministic unit tests and fault-injection / crash-recovery tests before moving on to the next layer.

### 3.1 State-Machine and Flag Hygiene

To prevent boolean-soup regressions in `StorageEngine` and adapter state machines, follow the architecture in [State-Machine Type Safety and Formal Verification Plan](plans/STATE_MACHINE_AND_FORMAL_VERIFICATION.md):

* **Own Per-Transaction State Inside `TxState`:** All per-transaction lifecycle control fields live privately inside `tx_fsm::TxCore` and payload buffers live inside `ActiveTxData`, paired under `TxState::InTx { core: TxCore, data: Box<ActiveTxData> }`. Returning to `TxState::Idle` drops `ActiveTxData` by value so no loose `tx_*` or `pending_tx_*` flags can leak across commits, group-commit handoffs, or rollbacks (`INV-TX-1`). Keep `TxPhase::FlushingWal` distinct so `RingFull` WAL rotations run without deferring while keeping pre-transaction `start_meta` authoritative during checkpoints. Do not add loose transaction fields back onto `StorageEngine`.
* **Pass Call-Frame Write Modes via `WriteScope`:** Pass `WriteScope::{Normal, InternalBypass}` explicitly as a parameter instead of mutating ambient mode booleans on `self` (`INV-TX-2`, `INV-TX-3`). `InternalBypass` preserves `TxPhase::Prepared`, `synced_vtabs`, and `sync_durability_upgrade`, whereas `Normal` enforces `max_transaction_bytes` and resets preparation back to `TxPhase::Active`.
* **Guard Temporary Latches With Private `#[must_use]` RAII Drops:** Encapsulate re-entrancy and phase latches (such as `reconciling_capped_table` and `relocating_std_blobs`) inside private field wrappers in `scoped_guards` whose `#[must_use]` RAII guard clears the state on `Drop` across normal returns, `?` early exits, and panics (`INV-TX-6`).
* **Eliminate `active: bool` Snapshot Sentinels:** Never represent an absent snapshot with `active: bool` or `Default` sentinels (as removed from `TxMetaSnapshot`); tie snapshot existence directly to the enclosing enum variant.
* **Gate Durable Writes Behind `HealthGatedStorage` / `HealthyEngine` (`INV-TX-4`):** Keep `BootMetaManager`, WAL writers, active blob writers, and `EngineHealth` private inside `mod health` (`src/engine/mod.rs`), requiring every durable mutation to acquire and consume a one-shot `HealthyEngine<'a, FS>` token via `try_healthy(&self.commit_gate)`. Keep read-path blob buffer flushes (`flush_buffered_blobs_for_read`, `ensure_blob_flushed_for_read`) and RAII `defer_barrier` unwind cleanup outside the mutation gate so poisoned engines remain readable and unwind cleanly.
* **Use Single-Lock `ConnDdlSlot` and `UniqueReadyLatch` in `src/vtab/`:** Maintain connection DDL phase (`Idle | StagedAutocommit(AutocommitDdl) | ExplicitTx { commit_hook, renames, renamed_handles }`) and `last_error` under one leaf mutex (`ConnDdlSlot` in [`src/vtab/ddl_slot.rs`](../src/vtab/ddl_slot.rs)) that is never held across `engine.write()`, `table_name.lock()`, or SQLite C API calls (`arm_tx_commit` allows same-connection `xCreate -> xSync` refresh on `AutocommitDdl::Create` while rejecting `Drop`, `Rename`, and overlapping phases). Access the per-vtab UNIQUE readiness latch exclusively through `UniqueReadyLatch` (`is_ready_for`, `latch_if_committed`, `invalidate`) in [`src/vtab/mod.rs`](../src/vtab/mod.rs) so sentinel `0` and uncommitted in-transaction markers can never be latched.
* **Isolate Pure Transitions in Sans-I/O `*_fsm.rs` Modules With Trace Replay (`M3`):** Keep transaction control fields private inside `TxCore` in [`src/engine/tx_fsm.rs`](../src/engine/tx_fsm.rs). Production code strictly above `// === TEST-ONLY SECTION ===` must contain zero `#[cfg(test)]` items and must never reference `std::io`, `std::fs`, `std::sync`, `std::thread`, `std::time`, `PlatformFs`, `PlatformFile`, `sqlite3`, or `unsafe` (enforced by `tx_fsm_production_code_has_no_io_lock_ffi_or_unsafe`). Route every transition through `tx_fsm::step` via `StorageEngine::apply_tx_event` and execute every returned `#[must_use]` `TxEffect` in the imperative shell. Under `#[cfg(test)]` (strictly below `// === TEST-ONLY SECTION ===`), `TxTraceRecorder` hooks `apply_tx_event` (preserving continuity across external poison latches), verifies exact step-by-step replay via `replay_verify()`, normalizes pointer-derived `conn_id`/`vtab_id` handles via `normalize_ids()`, and exports zero-dependency Schema v1 NDJSON via `to_ndjson()`.

### 3.2 Formal Verification Workflow

## 4. Living Textbook Documentation ("Build-to-Learn" Philosophy)

Documentation has three complementary layers, indexed by the [Documentation Guide](README.md): application usage guides, API references (including Rustdoc), and the design textbook. Follow [Public API Boundaries](reference/PUBLIC_API.md) when documenting new interfaces. A public Rust item is not automatically an application entry point. Keep application-facing operations separate from adapter protocols and implementation helpers; changes to code visibility or facade modules require explicit implementation and migration work.

For application API changes, update Rustdoc contracts, the relevant usage guide, and the [reference map](reference/README.md) together. Explain arguments, return values, errors, ownership/lifetimes, durability, and relevant concurrency rules. Guides should contain complete practical examples; textbook chapters retain the internal rationale rather than serving as the only usage manual. Planned features must be marked as planned. The native SQL frontend will need a separate execution API reference and language manual; vector search extends the native backend reference.

A core goal of the `aydb` project is to produce a **living, textbook-grade record of how a production-quality embedded database is designed and built from the ground up**. Design documents under `docs/` should read like chapters of a systems engineering textbook (in the spirit of *Database Internals* or *Designing Data-Intensive Applications*) rather than terse API notes:

* **Explain the "Why" and Fundamental Trade-Offs:** Do not merely state the chosen data structure or protocol. Contrast it with classic alternatives (e.g., B-Tree vs. LSM-Tree vs. WiscKey, user-space Buffer Pool vs. OS Page Cache delegation, double `fsync` vs. `Write-Blob-Before-WAL` with CRC verification) and explain the hardware and OS mechanics driving the decision.
* **Demystify OS & Filesystem Internals:** Explicitly document how the storage engine interacts with kernel subsystems—such as Windows Cache Manager 256 KB Virtual Address Control Blocks (VACBs), SMB Read-Write-Handle (RWH) leases, NTFS MFT metadata locking, antivirus minifilter behavior, and POSIX `pread`/`pwrite`/`fcntl` semantics.
* **Diagramming Standards:**
  * **Mermaid Diagrams:** Use for architectural overviews, read/write control flows, sequence diagrams, state machines, and module dependency graphs so they remain easy to diff and evolve inline.
  * **RFC-Style ASCII Box Diagrams:** Use for exact byte/bit offsets, sector headers, and fixed-size binary slot layouts.
  * **SVG Figures (`docs/assets/*.svg`):** Use when illustrating complex multi-layer memory/disk cross-sections or pointer topologies that require pixel-precise spatial alignment.


## 5. Crash-Consistency Tests

`src/engine/crash_tests.rs` drives the engine with a seeded random workload on a simulated filesystem (`CrashFs`), crashes it at a seed-chosen point, reopens it and compares the result with an oracle. Every run is determined by its seed.

**What `CrashFs` models**

* Each file has a page-cache image (what reads see) and a durable image (as of the last successful sync). A power loss lets each unsynced write persist completely, be lost, or persist only in the 512-byte sectors the seed picks. Later writes may persist while earlier ones are lost (reordering). A write that extends a file may extend its length without its data, which then reads as zeros.
* A process crash (`kill -9`) keeps the whole page cache and directory.
* `preallocate` with `PhysicalZeroFill` ends with a sync, as the real implementations do. `LogicalExtendOnly` is not durable until a sync.
* Directory entries follow the platform. Unix: `open_file` (create) and `remove_file` flush the directory, so entries are durable on return. Windows (assumption): the directory log is flushed by any successful `FlushFileBuffers`, and operations after the last flush survive as a random prefix, so an unflushed creation may be missing and an unflushed removal may be undone. Under both modes a data write never reaches the device before the directory operations issued before it. The mode is chosen per seed.
* Fault injection: a power cut at a global operation index (that operation and all later ones fail), or a one-shot failure of the n-th write, sync, pre-allocation, creation or removal on a chosen file kind (`boot_meta`, `wal_sync`, `wal_buf`, `idx`, blob, manifest). A failed sync may leave the writes pending, may have flushed them, or may drop them while later syncs succeed ("fsyncgate").

Not modelled: torn writes below 512 bytes, reordering within one write other than by sector, corruption of synced `boot_meta`/index/blob data (synced WAL corruption is exercised by the media-damage modes below), rename, multi-process access, and the real timing of group commit (the engine API is driven single-threaded).

**What the oracle checks** (ARCHITECTURE.md section 4)

The workload issues puts, overwrites, deletes, explicit transactions with savepoints, release and rollback, mixed durabilities, inline and out-of-line values, two capped tables, flushes, checkpoints, compaction, catalogs large enough to need a manifest (with table drops that shrink them), and small logs so that rotation collides with commits. The model keeps the state after every commit that was issued. After a crash the recovered state must equal the model state after `k` commits for some `k` between the last guaranteed commit and the newest issued one. This is the prefix property and atomicity at once. The guaranteed commit is:

* after a power loss: the last acknowledged `SyncTransactional` commit (it makes every earlier buffered commit durable) or successful `checkpoint`;
* after a process crash: the last acknowledged commit of either kind, and the state returned by an earlier recovery.

Interpretations: an operation that logged nothing (a delete of a missing row, a transaction without records) is not a commit and acknowledges nothing; a commit that returned an error while the engine is poisoned, or was interrupted by the power cut, may or may not be present; a failed operation on an engine that is not poisoned must have no effect and the workload continues; the capped tables evict on their own, so a row may be absent, but a present row must carry the value the model has for `k`. Reads must never fail. Reopen must succeed after any crash, including a second crash during or right after recovery, and must leave an engine whose `checkpoint` and `compact` work. After a checkpoint the state must survive another crash unchanged.

**Running**

For a hosted run, open **Actions → Trybot → Run workflow**, choose the branch, and set the first seed and count. Each of the three hosted operating systems runs the full regression suite and then the selected range in all four crash modes. The default covers seeds 4000 through 4999. Each job publishes its test logs as a workflow artifact. To investigate a failure, select the same revision, enter the failing seed, and choose a count of one.

The regular test runs 1,000 seeds (about 10 seconds in a debug build, on four threads). Environment variables:

* `AYDB_CRASH_SEEDS=<n>`: number of seeds (for example 2000 or more for a long run).
* `AYDB_CRASH_SEED_START=<n>`: first seed.
* `AYDB_CRASH_SEED=<n>`: replay one seed with the complete operation and filesystem trace in the failure report.

Each seed runs twice: once clean, which also measures the operation counts, and once with crash points and failures drawn from those counts.

Three more modes run the same harness (`src/engine/crash_tests/media.rs`), each with 150 seeds by default and the same environment variables (`AYDB_CRASH_SEEDS` applies to every mode):

* `crash_media_damage_seeds`: after the crash, synced WAL data is damaged (bit flips, zeroed sectors, a truncated file tail, an intact sector of an older epoch) in one or both streams, as the seed chooses. Copies of the damaged directory are opened under `Fail` (it must refuse exactly when damage is reported, and leave every file unchanged) and with `open_with_salvage` (whole transactions that the workload committed, above the replayed prefix); the real directory is then opened under `Truncate`. The oracle computes what the scan can see (it ends at a zeroed or older-epoch sector, the accepted limitation of ARCHITECTURE.md 4.6.4) and requires damage to be reported if and only if a lost batch lies at or below the highest `durable_lsn` of a visible batch.
* `crash_group_commit_seeds`: commits go through `begin_commit_for_conn` and are flushed later by a separate leader step, in a seed-chosen order on one thread (capped tables are not used, the engine does not group commits with them). The acknowledged-commit oracles are unchanged.
* `crash_group_commit_media_damage_seeds`: both.


**Bugs fixed after the harness found them.** (B) Reclaiming an LRU blob segment unlinked the file at once, so recovery dropped every log batch that still referenced it (and in the buffered stream every later batch), although a later synchronous commit had made them durable. The file now leaves the catalog at once but is unlinked only by the commit that rotates the WAL epochs (regression tests `reclaimed_lru_segment_keeps_batches_that_reference_it` and `reclaimed_lru_segment_is_unlinked_after_wal_rotation`); the workload therefore uses out-of-line values in capped tables. (C) Reclaiming an LRU blob segment synced `wal_buf.db` and recorded the buffered stream as durable without syncing the active blob writers, so a later synchronous commit skipped that sync and a buffered blob row could be lost although the synchronous commit was acknowledged; `make_buf_wal_durable` now syncs the blob writers itself (regression test `lru_reclaim_syncs_blobs_before_marking_buffered_commits_durable`). (D) Recovery used to adopt a blob segment that was queued in `pending_delete_files` when a stale pointer in an older `idx` segment referenced it, and then unlinked it in the same commit, so the next open failed with `NotFound`. Recovery now never adopts a file that is queued for deletion (regression test `pending_delete_of_dead_blob_segment_is_not_adopted`). (E) A failed buffered append that left a torn copy of the open `wal_buf.db` sector destroyed the earlier acknowledged batches packed into it, although BufferedFast must survive `kill -9`. `append_raw_batch` now rewrites the open sector's last good image on its error path, best effort (regression test `torn_buffered_append_keeps_earlier_batches_in_the_open_sector`). (F) The damage rule compared the cut that the chain names with `floor`, but a lost run of batches is named by its last member, so when an acknowledged batch and a later, never-durable batch were both lost the acknowledged loss went unreported (36 of 10,000 group-commit seeds with media damage); `judge` now reports damage iff `floor > last_good` and `first_lost_lsn` is `min(cut, floor)` (regression test `a_lost_batch_at_the_watermark_is_damage_although_the_chain_names_a_later_cut`). (G) The WAL writers preallocated each log file before recovery ran, so a file truncated by media damage was lengthened even when the open then refused under `WalDamagePolicy::Fail`; the engine now opens the streams unallocated and allocates after the `Fail` check (regression test `fail_policy_leaves_a_truncated_wal_file_untouched`; missing log files are also left uncreated until the `Fail` check passes, pinned by `fail_policy_with_a_missing_wal_file_refuses_without_creating_it`). (H) Autocommit `put_row`, `delete_row`, `backfill_secondary_keys` and the other writes outside a transaction read only the committed state and ignored a pending group commit, which left orphan secondary entries, row metadata and rowid mappings against the older row version; they now drain the pending group first (`drain_group_for_autocommit`; regression tests `delete_after_a_pending_group_commit_removes_its_secondary_entries`, `put_after_a_pending_group_commit_replaces_its_secondary_entries` and `backfill_after_a_pending_group_commit_finds_its_row`).

### 5.1 Multi-Connection Differential Oracle

[`src/vtab/multi_conn_diff_tests.rs`](../src/vtab/multi_conn_diff_tests.rs) (`multi_conn_mixed_native_ddl_compaction_matches_oracle`) opens two independent SQLite connections against the same engine and compares every query, error classification, and post-commit table state against mirrored native SQLite tables across interleaved DML, explicit transactions, savepoints, DDL (`CREATE`/`ALTER`/`DROP` including temporary-vtab pruning), `UNIQUE` index invalidation, `INSERT OR IGNORE`/`REPLACE`, `AUTOINCREMENT`, and concurrent background compaction.

* **Deterministic Seed Controls:**
  * `AYDB_MULTI_CONN_SEEDS=<n>`: number of consecutive seeds to run (default `20` in normal `cargo test`; set to `100` in `.github/workflows/trybot.yml`).
  * `AYDB_MULTI_CONN_SEED_START=<n>`: first seed index (default `0`).
  * `AYDB_MULTI_CONN_SEED=<n>`: replay one specific seed with full operation history on failure.
* **Trace Export Parity:** `export_formal_traces_multi_conn_diff` emits `tx_fsm_multi_conn_diff.ndjson` when `AYDB_EXPORT_TRACES_DIR` is set, keeping multi-connection DDL/savepoint/compaction sequences continuously checked against [`aydb-trace-check`](../formal/lean/TraceCheck.lean) in CI (`formal` job) alongside the committed baseline in [`formal/lean/fixtures/tx_fsm_multi_conn_diff.ndjson`](../formal/lean/fixtures/tx_fsm_multi_conn_diff.ndjson).
* **Scheduled Stress:** `.github/workflows/trybot.yml` runs on a weekly schedule (`0 4 * * 0` UTC) as well as manual `workflow_dispatch`, executing 100 seeds on Linux, macOS, and Windows.

### 5.2 Kani Bounded Verification Harnesses

Targeted `#[cfg(kani)]` harnesses verify bounded panic-freedom, bounds safety, and serialization roundtrips on compiled Rust code without adding any crates to `[dependencies]` in [`Cargo.toml`](../Cargo.toml) (`[lints.rust] unexpected_cfgs` enables `cfg(kani)` cleanly offline).

* **Scope (26 Harnesses):** [`src/engine/tx_fsm.rs`](../src/engine/tx_fsm.rs) (10 harnesses covering step invariants, savepoints, `WriteScope`, poison transitions, and `vtab_sync`), [`src/wal/mod.rs`](../src/wal/mod.rs) (4 harnesses covering arbitrary byte decode safety, inline/delete/marker/BlobPtr roundtrips, and batch CRC validation), [`src/index/mod.rs`](../src/index/mod.rs) (5 harnesses covering block header bounds, accessor safety, layout validation, and binary search across inline, tombstone, and BlobPtr entries), and [`src/vtab/row_codec.rs`](../src/vtab/row_codec.rs) (7 harnesses covering decode safety, collations, row roundtrips, and order-preserving memcomparable encodings).
* **Execution Environment:** Run natively on Linux (`trybot.yml` `kani` job pinned to Kani `0.68.0`) or inside WSL2 on Windows (`cargo kani --lib`). Standard `cargo test --all-targets` and `cargo clippy --all-targets -- -D warnings` remain unaffected offline without Kani installed.
* **Authoring Conventions for Tractable CBMC Proofs:**
  * Route recoverable error creation in Kani-verified paths through `crate::util::io_err` / `io_err_with_tag` (returning zero-allocation `std::io::Error::from(kind)` under `cfg(kani)`) and check `io::Result<T>` inside harnesses via a local `unwrap_io` helper using `std::mem::forget` on the `Err` branch so CBMC does not unwind recursive `io::Error::drop` gluings.
  * Guard external FFI link attributes (`#[cfg_attr(all(unix, not(kani)), link(name = "sqlite3"))]`) and hardware SIMD dispatch (`crc32c` bitwise fallback under `kani`) cleanly without introducing `#[allow]` or `#[expect]` suppressions.
  * Dispatch variable-length encoder/decoder roundtrips inside concrete-size match arms and use loop-free fixed-byte indexing rather than symbolic-size heap allocations or `.try_into().unwrap()`.
  * Avoid pointer-vs-integer union overlays in enums decoded under CBMC (keep borrowed decoder intermediate enums index/span-based using `Range<usize>`, as in `BorrowedWalRecord`).
